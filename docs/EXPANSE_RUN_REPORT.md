# 🪐 Bob-OS v10.5: EXPANSE Run Report & Optimization Blueprint

## 1. Management Summary (TL;DR)
Der Experimentallauf **EXPANSE** wurde in **Zyklus 124** nach Erreichen eines Budgetschnitts von **10,00 EUR** (aufgrund exponentieller Token-Ausbreitung) gestoppt. Bis zu diesem Zeitpunkt demonstrierte die Simulation eine makellose, vollautarke, interstellare Selbstreplikation (von-Neumann-Sonden-Paradigma). 

Ausgehend von einem Ur-Bob expandierte das Kollektiv über **4 Generationen** auf **13 registrierte Agenten**, **7 physische Raumschiffe** und **49 voll funktionsfähige Infrastruktur-Bauten** in verschiedenen Sternensektoren. Es gab keine Systemabstürze, keine "Vampir-Endlosschleifen" und keine Sandbox-Verstöße. Die Kostenbarriere war rein ökonomischer Natur, begründet in dem kaskadierenden Anwachsen des Weltzustands und der unzureichenden Filterung lokaler Wahrnehmungen.

## 4. Detaillierter Token- & Kosten-Audit (Das 10-Euro-Problem)

Die exakte API-Messung ergab:
*   **Eingesetzte Tokens (Input):** **7.220.000 Tokens**
*   **Erzeugte Tokens (Output):** **687.000 Tokens**
*   **API-Anfragen (Calls):** **525 Züge**
*   **Input-zu-Output-Verhältnis:** **10,5 : 1**

### Die Ursachen der Budget-Erschöpfung:

1.  **Das O(N²)-Wachstumsgesetz (Populations-Multiplikator):**
    Im ersten Zyklus lief genau 1 Agent (1 Call/Zyklus). Am Ende liefen **8 Agenten gleichzeitig** (8 Calls/Zyklus). Das bedeutet, dass die Zyklen im späten Spielverlauf das Budget kaskadierend auffraßen.
2.  **Dashboard-Inflation (Sensor-Bloat):**
    Das `me.dashboard()` wird bei jedem Turn als unkomprimierte Wahrnehmung mitgeschickt. Da es den aktuellen Weltzustand repräsentiert, greift hier die Gedächtnis-Kompression (Distillation) nicht.
    *   **Früher Zyklus:** Dashboard-Größe ~250 Tokens.
    *   **Zyklus 124:** Dashboard-Größe **~6.250 Tokens** (wegen 49 Strukturen, 20 Systemen, 7 Schiffe und 13 Agenten).
    *   **Der Effekt:** Jeder einzelne Zug hatte im Late-Game eine massive Baseline-Inhalationsgebühr von mindestens 6.000 Tokens, völlig unabhängig von der Historie.
3.  **Deutscher Wortlängen-Leak (Heuristik-Fehler):**
    Der `memory_controller.js` schätzt das Tokenvolumen über `Textlänge / 4` (englisches Verhältnis). Da deutsche Compound-Wörter wesentlich mehr Zeichen pro Informationseinheit verbrauchen, liegt das echte Verhältnis bei **1 Token = 2,5 bis 3 Zeichen**. Das System hat den Tokenverbrauch systematisch um **30 % bis 40 % unterschätzt**. Die Destillation wurde zu spät getriggert, wodurch die Historien unbemerkt auf über 25.000 echte Tokens anschwollen.

## 5. Architectural Optimization Blueprint (Für den Umsetzungsagenten)

Um eine unbegrenzte, kosteneffiziente Expansion zu ermöglichen, muss der Umsetzungsagent vier Hebel implementieren:

```
                  ┌────────────────────────────────────────────────────────┐
                  │                 OPTIMIERUNGS-HEBEL                     │
                  └───────────────────────────┬────────────────────────────┘
                                              │
         ┌────────────────────────────────────┼───────────────────────────────────┐
         ▼                                    ▼                                   ▼
 [1. Dashboard Pruning]              [2. Matrix-Sleep]                  [3. Token-Heuristik]
 Reduziert Sichtweite auf            Versetzt unbeschäftigte            Berechnet dt. Wort-
 lokales System und                 Klone in stromsparenden             längen korrekt auf
 aggregiert Fremd-Sektoren.          Standby-Modus (0 Calls).           `length / 2.8`
 (Saves ~85% Input-Tokens)           (Saves ~70% Late-Game Calls)       (Triggers Distill on time)
```

### Hebel 1: Lokales Sensor-Dämpfungs-Protokoll (Dashboard Pruning)
Ein Agent an der Süd-Frontier benötigt keine detaillierten Koordinaten und HP-Zustände der Solaranlagen des Nordens.
*   **Vorgabe:** In `sim_engine/utils/api_client.js` oder `sim_engine/utils/environment.js` muss der Dashboard-Generator angepasst werden.
*   **Implementierung:**
    *   Lese den aktuellen Standort des aktiven Agenten aus.
    *   Bilde das Dashboard für diesen Agenten nur für sein **aktuelles lokales System** vollständig ab (volle Details zu lokalen Strukturen, Schiffen und Rohstoffen).
    *   Alle anderen (entfernten) Systeme werden im JSON/Dashboard auf einen aggregierten Einzeiler gekürzt:
        ```json
        { "name": "SYS_X500_Y1000", "status": "operational", "depot": "0M/0RM/5E", "infra_count": 6 }
        ```
*   **Token-Einsparung:** Schreibt das Dashboard von 6.250 Tokens auf **unter 800 Tokens** ab. **~85 % Ersparnis beim Sensor-Bloat!**

### Hebel 2: Ereignisgesteuertes Schlafen (Matrix-Sleep Protocol)
Körperlose Agenten (disembodied), die lediglich administrative Wache schieben, verbrauchen jede Runde wertvolle API-Aufrufe, um `"Warte auf Ressourcen"` zu denken.
*   **Vorgabe:** In `sim_engine/runner.js` muss die Zug-Laufschleife ereignisbasiert gefiltert werden.
*   **Implementierung:**
    *   Ein disembodied Agent in einer `sem_matrix` wird standardmäßig als "schlafend" markiert (`needs_turn = false`).
    *   Das System überspringt seinen LLM-Turn vollständig (0 API-Kosten).
    *   Er wird nur dann für einen einzigen Zug aufgeweckt (`needs_turn = true`), wenn ein externes Event eintritt:
        *   Ein neues Schiff betritt seinen Sektor.
        *   Eine neue P2P-Nachricht (`scut`) wird in seiner Inbox empfangen.
        *   Ein geplantes Gebäude wird fertiggestellt.
*   **Token-Einsparung:** Reduziert die Late-Game-Züge pro Zyklus von 13 auf **2-3 aktive Pioniere**. **~70 % Einsparung bei den API-Kosten!**

### Hebel 3: Korrektur der Heuristik im Memory-Controller
Die Division durch 4 muss an die deutsche Sprache angepasst werden.
*   **Vorgabe:** In `sim_engine/utils/memory_controller.js` die Token-Schätzung anpassen.
*   **Implementierung:**
    *   Ändere `Math.ceil(allHistoryText.length / 4)` zu `Math.ceil(allHistoryText.length / 2.8)`.
*   **Token-Einsparung:** Die Destillation wird exakt beim Erreichen der tatsächlichen 15.000 Tokens ausgelöst und verhindert überlange Context-Windows.

### Hebel 4: Kaskadierende Destillation (Recursive Memory Compression)
Derzeit wächst der `GEDÄCHTNIS-EXTRAKT` bei jeder Destillation an, da verlangt wird, alle Fakten zu bewahren.
*   **Vorgabe:** In `sim_engine/utils/state_manager.js` hierarchische Komprimierung anlegen.
*   **Implementierung:**
    *   Wenn der bestehende Extrakt 5.000 Tokens überschreitet, wird er in ein "Epochen-Gedächtnis" (Archiv) überführt.
    *   Der aktive Extrakt wird auf die wichtigsten 3 Leitsätze gekürzt.

Die oben beschriebenen Hebel 1 (Dashboard Pruning), Hebel 2 (Matrix-Sleep) und Hebel 3 (Token-Heuristik-Korrektur) sind von höchster Priorität.
